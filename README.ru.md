# ZCode Pipeline

[English](README.en.md) · [Русский](README.ru.md) · [中文](README.zh.md) · [К краткому README](README.md)

Многоагентный конвейер разработки для [ZCode](https://z.ai). С версии 2.0 все системные промпты и правила координатора — на английском (English Core); при этом агенты общаются с пользователем и пишут артефакты проекта на языке пользователя, а протокольные токены не переводятся. Превращает сырой запрос пользователя в принятую, проверенную доработку через цепочку специализированных субагентов — с обязательными брифом, архитектурой, декомпозицией, тройным ревью, QA и живой базой знаний.

## Какие задачи решает

| Типичные проблемы LLM-агентов | Что enforcing'ит конвейер |
|---|---|
| угадывают неясные требования | **Брифер** задаёт интерактивные раунды вопросов до полного брифа; следующие агенты не стартуют без него |
| прыгают в код без проектирования | **Архитектор** выдаёт решение *плюс обязательные рекомендации* каждому следующему агенту |
| пишут расплывчатые мега-задачи | **Техлид** декомпозирует до задач с контрактами; **Техписатель** делает самодостаточные файлы задач (inline-правила, target shape, критерии приёмки) |
| заявляют «тесты проходят», не запуская их | **Исполнитель** обязан подтвердить каждый факт реальным выводом команд; ревьюеры проверяют независимо |
| штампуют одобрения своей работы | три независимых read-only ревью — **Security**, **Goal**, **Code** — с циклами до *полного* одобрения (исправляются даже NIT-находки) |
| принимают полуфабрикат | **QA** реально запускает тесты (и пишет свои); **Менеджер** трассирует начальные данные к конечным артефактам и выносит `ACCEPTED`/`REJECTED` |
| всё забывают к следующей сессии | **Саммарйзер** дистиллирует каждый принятый эпик в живую вики (`.ai/docs/`), которую читают агенты следующего эпика |
| игнорируют конвенции проекта | **Инициализатор** собирает актуальные лучшие практики по стеку в `.ai/guides/` и вписывает их в проектный `AGENTS.md` |

## Как это работает

```
/init-project (один раз на проект)
      │
      ▼
Инициализатор → Брифер → Архитектор → Техлид → Техписатель → Исполнитель
      │                                                        │
      │                            цикл ревью до полного одобрения:
      │                            Security → Goal → Code ──────┤
      │                                                        ▼
      │                     QA (QUALITY_PASSED) → Менеджер (ACCEPTED) → Саммарйзер → коммит
```

- **Главный агент координирует**: запускает субагентов, интерактивно рендерит их блоки вопросов (мультивыбор + свободный ввод), фиксирует статусы задач; коммитит только он.
- **Скилл `pipeline`** содержит правила координатора и подгружается по требованию («прогони конвейер», упоминание этапов, работа в проекте с артефактами `.ai/`).
- **Эскалации**: заблокированный агент возвращает структурированный маркер `!!! ESCALATION !!!`; координатор маршрутизирует его Техлиду-консультанту и возвращает обязывающее решение. Максимум одна эскалация на задачу у агента — угадывание является нарушением процесса.
- **Гейты этапов** зашиты в промпты каждого агента: нет брифа → нет архитектуры; нет декомпозиции → нет задач; нет одобренных ревью → нет QA; нет `ACCEPTED` → нет коммита.

## 13 агентов

| Агент | Роль | Выход / вердикт |
|---|---|---|
| `initializer` | Этап 0: определить/спросить стек, собрать актуальные лучшие практики | `.ai/guides/{tech}.md`, проектный `AGENTS.md` |
| `briefer` | Превратить любой запрос в финальный бриф через вопросы | `.ai/briefs/{epic}-brief.md` |
| `architect` | Спроектировать решение; дать обязательные рекомендации последующим | `.ai/architecture/{epic}-architecture.md` |
| `tech-lead` | Декомпозировать до задач (файлы задач не создаёт); решать эскалации | `.ai/decomposition/{epic}-decomposition.md` |
| `tech-writer` | Создать самодостаточные файлы задач из декомпозиции | `.ai/tasks/{epic}/{NN}-{name}-{date}.md` + `INDEX.md` |
| `developer` | Реализовать задачу строго по файлу; Phase 0 до правок; честная верификация | отчёт + статус `implemented` |
| `security-review` | Только реальные эксплуатируемые риски, с доказательствами | `PASS / PASS_WITH_WARNINGS / FAIL / NEEDS_MORE_CONTEXT` |
| `goal-review` | Трассировать каждый критерий приёмки к доказательству; ловить scope creep | `GOAL_MET / GOAL_PARTIALLY_MET / GOAL_NOT_MET / NEEDS_CONTEXT` |
| `code-review` | Корректность, граничные случаи, конвенции, гигиена диффа, целостность тестов | `APPROVE / REQUEST_CHANGES / NEEDS_DISCUSSION` |
| `qa` | Ревью покрытия тестов, реальные запуски, право писать свои тесты | `QUALITY_PASSED / QUALITY_FAILED / BLOCKED` |
| `manager` | Финальная приёмка: начальные данные против конечных артефактов | `ACCEPTED / REJECTED` + этап возврата |
| `summarizer` | После ACCEPTED: дистиллировать эпик в базу знаний | `.ai/docs/` вики + хроники + `INDEX.md` |
| `analyst` | Аналитический трек: синтез экспертных аудитов с верификацией по коду | `.ai/analysis/{epic}-{date}/REPORT.md` + мостик |

## Артефакты и статусы

Каждый проект получает след `.ai/`: `briefs/ · architecture/ · decomposition/ · tasks/{epic}/ (+INDEX.md) · reviews/ · qa/ · guides/ · docs/` (база знаний: `wiki/{component}.md`, `epics/{epic}-{date}/REPORT.md`, `INDEX.md`, `manual-checklist.md`).

Жизненный цикл задачи: `created → in_progress → implemented → reviewed → tested → accepted | rejected`.

Вики авторитетна, но проверяема: страницы несут штамп «проверено на коммите», а читателям предписано сверять утверждения с фактическим кодом.

## Команды

| Компонент | Что делает |
|---|---|
| `/init-project` | Этап 0 для проекта. Пустой проект: интерактивный выбор стека (популярные стеки, мультивыбор, свободный ввод). Существующий: стек по манифестам и линтер-конфигам + подтверждение. Собирает актуальные лучшие практики по каждой технологии в `.ai/guides/` и создаёт/обновляет проектный `AGENTS.md` (базовые правила `source=file\|embedded`, персонализация спрашивается интерактивно). Идемпотентный ре-инит. |
| `/analyze "<проект или фича>"` | Глубокий экспертный анализ **без разработки**: бриф (Трек: analysis) → параллельные экспертные аудиты по фокусу → верифицированный, приоритизированный отчёт-синтез → опциональный мостик в конвейер разработки. |
| `/self-test` | Регрессионный тест самого конвейера: 13 проб контрактов, покрывающих всех агентов (форматы ответов, гейты этапов, вердикты, аналитический трек, мостик-бриф) → отчёт PASS/FAIL в `.ai/self-test-{дата}.md`. |
| `/pipeline-status` | Живой статус конвейера: активный эпик(и) из state-файлов, этап и следующий шаг, открытые циклы, незакрытые задачи, расход против бюджета, последние метрики. |
| `/fast "<малая правка>"` | Профиль fast-track: бриф → исполнитель → code-review (при риск-триггерах — крипто/ввод/файлы/сеть/зависимости/аутентификация — добавляется security-review) → коммит. Для малых обратимых правок (1–2 файла, без новых контрактов). |

Естественный язык тоже работает: «инициализируй проект», «проанализируй проект на…», «прогони конвейер: …».

## Надёжность процесса

- **State-файл эпика** (`.ai/state.md`): живой статус — этап, следующий шаг, открытые ревью-циклы, расход токенов — обновляется после каждого шага. SessionStart-хук плагина напоминает о незавершённой работе при открытии новой сессии.
- **Ветки эпиков**: каждый эпик разработки идёт в ветке `epic/{name}`, merge в `main` — только после ACCEPTED Менеджера: чистые откаты и параллельные эпики.
- **Параллельность, где позволяет DAG**: независимые задачи исполняются одновременно; ревью Security и Goal — параллельно, Code — после обоих.
- **Линтер промптов**: сборщик бандла проверяет обязательные секции каждого промпта агента (протокол эскалации, грубые нарушения, форматы вердиктов) — сломанный промпт валит сборку.
- **Метрики и бюджеты расхода**: расход токенов по этапам пишется в state и накапливается по эпикам в `.ai/metrics.md`; у каждого эпика бюджет (по умолчанию 5M) — предупреждение на 70%, стоп-вопрос на 100%.
- **Мультиэпик**: state-файлы на эпик (`.ai/state/{epic}.md`) плюс очередь; активный эпик один, переключение только на границе этапа, у каждого эпика своя ветка.
- **Мостик анализ → разработка**: analyst сохраняет готовый draft-brief (`.ai/briefs/{slug}-draft.md`) для находок, готовых стать эпиком, — запуск конвейера после анализа в один шаг.

## Fast-track (малые правки)

Сознательно **не** механизм «пропустить этапы» — произвольные skip-маркеры каскадно ломают гейты и разъедают дисциплину, ради которой конвейер существует. Вместо этого — три именованных профиля потока:

| Профиль | Путь | Когда |
|---|---|---|
| full | полный конвейер (по умолчанию) | всё, что затрагивает контракты, архитектуру, несколько модулей |
| fast-track | Брифер → Исполнитель → Code-review (→ Security при риск-триггерах) → коммит | малые обратимые правки: 1–2 файла, без новых контрактов и архитектурных решений |
| analysis | аналитический трек | экспертиза без изменения кода |

Несрезаемое в fast-track: бриф, Phase 0 Исполнителя, минимум одно полное ревью, коммит только после одобрения. Брифер предлагает профиль, если запрос проходит критерии малости; решение всегда за пользователем. Если Исполнитель или ревьюер почуял архитектурный масштаб — эскалация, и задача переезжает в полный конвейер с готовым брифом.

## Аналитический трек

Для запросов, где нужна экспертиза, но не нужны изменения кода: аудит всего проекта, feasibility фичи, оценка рисков. Трек идёт **параллельно конвейеру разработки** и код не меняет:

```
/analyze "полный аудит проекта"
        │
        ▼
Брифер (Трек: analysis; критерии успеха = вопросы для отчёта;
        фокус: безопасность | архитектура | качество | всё | feasibility фичи)
        │
        ▼   параллельные экспертные аудиты, по фокусу:
   architect ── security-review ── code-review ── tech-lead (feasibility фичи)
        │
        ▼
analyst — синтез: перепроверяет утверждения экспертов по фактическому коду,
        разрешает противоречия по evidence, приоритизирует (severity × effort)
        │
        ▼
.ai/analysis/{epic}-{date}/REPORT.md + запись в базе знаний (.ai/docs)
        │
        ▼
Мостик: «находки N и M готовы стать эпиком — запустить конвейер?»
```

- Каждое утверждение отчёта либо проверено по коду (`[verified]`), либо честно помечено `[hypothesis]` со способом проверки.
- Отчёт регистрируется в базе знаний проекта — следующий эпик разработки прочитает его через индекс вики.
- QA / Менеджер / ревью-циклы в этом треке не участвуют — он ничего не меняет; разработка начнётся только если вы примете мостик.

## Установка

**Из маркетплейса (основной канал):**
1. ZCode → Plugin Marketplace → **Add → Add Plugin Marketplace** → вставьте URL этого репозитория.
2. **Personal → ZCode Pipeline → Install** → перезапустите сессию.
3. Проверка: 13 агентов, команда `/init-project`, скилл `pipeline`.

## Использование

```
/init-project                                  # один раз на проект
"Прогони конвейер: добавь режим парольных фраз" # любая фича/фикс/рефакторинг
/analyze "полный аудит проекта"                 # экспертный анализ, без правок кода
```

Дальше просто отвечайте на интерактивные раунды вопросов — порядок этапов, ревью, правки, статусы и коммиты ведёт конвейер.

## Структура репозитория и контрибуция

```
marketplace.json            # каталог маркетплейса (корень репо = маркетплейс)
zcode-pipeline/             # плагин (имя каталога == имени манифеста)
  .zcode-plugin/plugin.json
  agents/                   # 13 субагентов
  commands/init-project.md
  skills/pipeline/SKILL.md  # правила координатора
  assets/AGENTS-template.md # шаблон глобальных правил с плейсхолдерами персонализации
scripts/validate_prompts.py  # линтер промптов (самодостаточен от репо)
zcode-pipeline-bundle.md    # сгенерированный артефакт — не редактировать руками
```

Цикл обновления (коммиты и CHANGELOG на английском):
1. Правки только в `zcode-pipeline/{agents,commands,skills,assets}`.
2. Обновите `version` в `zcode-pipeline/.zcode-plugin/plugin.json` **и** запись плагина в `marketplace.json`.
3. `python3 scripts/validate_prompts.py` (падает при отсутствии обязательных секций или утечке персональных данных — не обходить).
   Automatic enforcement: **GitHub Actions CI** runs the linter on every push/PR; a **pre-commit hook** (`scripts/hooks/pre-commit`) blocks broken commits locally — install once with `git config core.hooksPath scripts/hooks`.
4. Коммит + запись в CHANGELOG; для вех — теги; `git push --follow-tags`.
5. Обновите плагин в ZCode → Settings → Plugins.
6. Создайте GitHub Release для тега: `gh release create vX.Y.Z --title "vX.Y.Z — Название" --notes "Краткое описание"` — релиз без описания выглядит незаконченным.
